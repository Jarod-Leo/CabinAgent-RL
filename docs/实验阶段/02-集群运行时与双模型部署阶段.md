# 02 集群运行时与双模型部署阶段

## 状态

已完成。

## 目标

- 在项目 SSD 中建立可复现的 CUDA/Conda/veRL/vLLM 环境。
- 部署 Qwen2.5-72B-AWQ user simulator 和 Qwen2.5-7B policy。
- 验证同一物理节点双 GPU 原子申请、服务互联和缓存位置。

## 设置

| 角色 | 设置 |
|---|---|
| Simulator | `Qwen/Qwen2.5-72B-Instruct-AWQ`，vLLM，AWQ-Marlin，TP=1 |
| Policy | `Qwen/Qwen2.5-7B-Instruct`，vLLM/veRL |
| 拓扑 | 同一台 highmem Pro 6000 物理节点，共 2 GPU；一个 srun step 内两个 task 各 1 GPU |
| Simulator context | `8192` |
| Simulator batching | `max_num_seqs=16`，`max_num_batched_tokens=32768` |
| Policy context | prompt `24576` + response `8192` = `32768` |
| 缓存 | vLLM、Triton、TorchInductor、HF、Ray 和临时缓存全部定向项目 SSD |
| 调度 | `cluster02`，account/QoS `msc`，`--nodes=1 --gres=gpu:pro6000:2`，`--constraint=highmem` |

### 2026-09-01 单节点双 GPU 拓扑改进

#### 实验设置

- G03 与正式 GRPO 均固定为 `--nodes=1 --gres=gpu:pro6000:2 --constraint=highmem`。
- 一个 srun step 使用 `--ntasks=2 --gpus-per-task=1 --gpu-bind=single:1`；task 0 运行 simulator，task 1 运行 policy/trainer，通过 `127.0.0.1` 通信。
- 每个作业保存 Slurm stdout/stderr，以及 allocation、simulator、policy/trainer、rollout/gate-check 独立日志。

#### 执行结果

- 实时 QoS 确认 `msc` 允许每用户最多 2 块 Pro 6000；集群存在单节点 4/8/10 卡 Pro 6000 节点，可满足同节点双卡申请。
- 2026-09-01 检查时用户队列为空，highmem Pro 6000 均已分配，因此新作业预计先进入排队。
- 本地静态回归测试已确认两个双 GPU sbatch 均为单节点申请，尚待远端 `bash -n` 与 `sbatch --test-only`。

#### 改进原因

- 集群规则明确禁止一个任务跨多个物理节点组合 GPU；旧 G00-G03 脚本的 `--nodes=2` 拓扑不再允许继续使用。
- 分组件日志可以区分资源绑定、模型服务、rollout、gate-check 和 trainer 故障。

#### 改进措施

- 将 gate 和 GRPO sbatch 改为单节点双 GPU，并删除 hostname 角色拆分。
- 新增 allocation 资源审计日志和 Job ID 命名的组件日志。
- 提交前必须在集群执行 shell syntax、配置断言和 Slurm test-only；实际运行后核对 allocation 日志中的单一节点和两块 GPU。
- 正式 G03 前先执行 10 分钟上限的同节点双 GPU 绑定 smoke；两个并发 step 的 `SLURM_STEP_GPUS` 必须非空且互不相同，G03 通过 `afterok` 依赖该 smoke。

### 同节点双 GPU smoke attempt 1 / Slurm 132933

#### 实验设置

- `--nodes=1 --gres=gpu:pro6000:2 --constraint=highmem`，两个后台 `srun` 各申请 1 块 Pro 6000。
- 保存 Slurm stdout/stderr、allocation 和两个 step 日志，并比较 `SLURM_STEP_GPUS`。

#### 执行结果

- Slurm 在同一物理节点 `gpu-pro6000-7` 分配了两块 GPU，Job GRES 为物理索引 `0,4`。
- 两个 step 均以 `0:0` 完成，但都记录 `SLURM_STEP_GPUS=0` 和同一 UUID；batch 校验因此正确返回失败，作业 `132933` 最终状态 `FAILED`，耗时 1 秒。

#### 改进原因

- Step 只执行一次 `nvidia-smi` 就退出，两个后台请求没有形成稳定的并发重叠；第二个 step 在第一块 GPU 被释放后复用了 GPU 0，无法验证长驻双服务的并行绑定。

#### 改进措施

- 每个 step 在记录绑定后保持 10 秒，使两个 GPU allocation 同时存活，再比较 `SLURM_STEP_GPUS` 和 UUID。
- 使用新 Job ID 提交 attempt 2；旧 132933 日志完整保留。G03 必须依赖新的 smoke PASS，不能依赖 132933。

### 同节点双 GPU smoke attempt 2 / Slurm 132950

#### 实验设置

- 在 attempt 1 基础上让两个独立 one-GPU `srun --exclusive` step 各保持 10 秒，尝试形成稳定并发。

#### 执行结果

- 作业在 `gpu-pro6000-7` 获得两块 GPU，但 step `132950.0` 与 `132950.1` 仍串行运行，各 10 秒；batch 最终 FAIL。

#### 改进原因

- 集群为每个 exclusive step 继承了作业级内存资源，导致第二个 step 等待第一个释放，无法同时启动 simulator 和 policy。

#### 改进措施

- 放弃两个独立 srun step，改为一个 srun step 内启动两个 task：`--ntasks=2 --gpus-per-task=1 --gpu-bind=single:1`。
- 新 smoke 直接比较两个 task 的 GPU UUID；G03 使用相同绑定模型并通过 task role 分工。

### 同节点双 GPU smoke attempt 3 / Slurm 132966

#### 实验设置

- 单一 srun step、两个 task，`--gpus-per-task=1 --gpu-bind=single:1`；每个 task 记录 hostname、CUDA 可见设备和 GPU UUID。

#### 执行结果

- 作业 `132966` 在 `gpu-pro6000-3` 完成，耗时 10 秒，退出码 `0:0`。
- Task 0/1 分别获得 UUID `GPU-bd67f840-...` 与 `GPU-d9b859d6-...`，同节点且 GPU 不同，输出 `SAME_NODE_DUAL_GPU_OK`。

#### 改进原因

- Attempt 1/2 证明独立 exclusive step 会串行复用 GPU，必须在同一个 step 内完成并发 task 绑定。

#### 改进措施

- 将单-step双-task绑定设为 G03 和后续 GRPO 的唯一合法启动模型。
- G03 allocation 与 role 日志必须核对 `NumNodes=1`、`gres/gpu:pro6000=2` 和两个 role 正常启动。
